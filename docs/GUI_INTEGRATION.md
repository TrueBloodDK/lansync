# Основа GUI-клиента для LANSync 0.1.0

CLI-ядро можно использовать для разработки GUI. Передача файлов, конфликты,
блокировки, TLS и recovery остаются ответственностью ядра. GUI хранит настройки
проекта, запускает операции и показывает результаты. Серверный протокол для
первого GUI менять не требуется.

## Два способа подключения

Python-интерфейс может вызывать ядро из рабочего потока. Для длительного режима
`lansync.sync_loop.continuous_sync` принимает `threading.Event` в `stop`,
`on_event` для состояния и `on_progress` для передачи. Кнопка остановки выставляет
Event; UI остаётся отзывчивым и ждёт завершения текущего прохода. HTTP-клиент
создаётся и закрывается в том же рабочем потоке. Сигналы GUI передают результаты
в главный поток; callbacks ядра не должны напрямую менять виджеты.

Приложение на другом языке может запускать CLI с аргументами отдельным массивом,
без shell и конкатенации команд. Для настройки, плана и диагностики подходят
JSON-команды ниже. Управление длительным процессом на Windows потребует отдельного
локального канала штатной остановки: TerminateProcess и остановка задания могут
оставить lock. Такой канал пока не реализован. Не выдавать принудительную остановку
за обычную кнопку «Пауза». Это задача адаптера GUI, не изменение сетевого протокола.

Python-функции пока не обещают независимой совместимости между версиями.
GUI и ядро следует выпускать с согласованными версиями и проверять интеграционно.
Выбор технологии UI остаётся отдельным решением; компилируемый язык не требуется
для использования этого ядра.

## Существующие операции

| Назначение | CLI |
|---|---|
| Создать проект | `lansync init PATH --mode client --url URL` |
| Проверить конфигурацию | `lansync run CONFIG --check` |
| Проверить локальные пути и реквизиты | `lansync inspect CONFIG --json` |
| Проверить соединение | `lansync run CONFIG --action doctor --json` |
| Предварительный план | `lansync run CONFIG --action plan --json` |
| Один проход | `lansync run CONFIG --action once` |
| Непрерывная работа | `lansync run CONFIG` |
| Снимок состояния | `lansync run CONFIG --action status --json` |
| Список копий | `lansync run CONFIG --action recovery-list --json` |
| Проверка копий | `lansync run CONFIG --action recovery-verify --json` |
| Экспорт копии | `lansync run CONFIG --action recovery-restore --id ID --output NEW_FILE` |
| Решение конфликта | `lansync run CONFIG --action resolve --path PATH --choose local` |

Для разрешения конфликта также есть `remote` и `both`; для `both` нужен новый
относительный `--copy-path`. Перед resolve и другими изменяющими командами GUI
останавливает собственный непрерывный цикл и ждёт освобождения состояния.
JSON поддерживается только явно перечисленными действиями. Текстовый вывод
`once`, `start`, `resolve` не является JSON и не должен разбираться как Python-код.
Успех завершённой CLI-команды — код 0; ошибку необходимо учитывать вместе с stderr.
При sync код 2 также обозначает обнаруженные конфликты; argparse использует код 2
для ошибки аргументов. Значение нужно интерпретировать в контексте операции,
а список конфликтов читать из сохранённого отчёта, не угадывать по одному коду.

Статус содержит `lock_present`, `loop`, `last_sync`, `loop_report_older`.
`loop` может отсутствовать; его состояния — starting, retrying, conflicts,
synced, stopped, failed. Это сохранённые данные: `synced` не доказывает, что процесс
жив или сервер доступен сейчас. GUI отдельно отслеживает свой worker/процесс
и показывает время последнего успешного прохода.

## Границы первого интерфейса

Первый GUI: добавление проекта, проверка соединения, запуск/остановка,
состояние и ошибки, предварительный план, конфликты, список и экспорт recovery.
Настройку автозапуска и упаковку автономного приложения можно добавить отдельно.

- Один владелец синхронизации для одного state_dir; не запускать параллельные sync.
- Не удалять stale-lock или pending автоматически при запуске интерфейса.
- Не редактировать SQLite, baseline и recovery вручную ради обновления экрана.
- Токен брать из файла реквизитов, не передавать в командной строке и не писать в лог.
- Не отключать проверку TLS при ошибке соединения.
- При закрытии GUI дождаться штатной остановки либо оставить управляемую работу
  в фоне с явным состоянием. Убийство рабочего потока недопустимо.

Проверки GUI должны включать остановку во время передачи, недоступный сервер,
конфликт, повторный запуск после аварии и недопущение двух владельцев состояния.
Готовность CLI подтверждена отдельно; эта страница не означает, что GUI уже создан.
