# Двусторонняя синхронизация с ревизиями

Команда `sync` выполняет один проход обмена. Она отправляет новые/изменённые
локальные файлы, скачивает серверные изменения и передаёт удаления. Каталоги
создаются вместе с родителями, удаляются только пустыми, начиная с самых глубоких.
По умолчанию выполняется один проход; `--watch` включает непрерывные проходы.

Подготовка сертификатов и токена описана в [NETWORK.md](NETWORK.md).

## Запуск

Обновите установку: `python -m pip install -e ".[dev]"`.
Уже настроенный сервер запустите с дополнительным флагом `--allow-write`:

```powershell
lansync serve "C:\Users\dkara\Documents\Shared" --state-dir "C:\Users\dkara\Documents\lansync-state" --host 0.0.0.0 --token-file "C:\Users\dkara\Documents\lansync-credentials\token.txt" --cert-file "C:\Users\dkara\Documents\lansync-credentials\server.pem" --key-file "C:\Users\dkara\Documents\lansync-credentials\server-key.pem" --allow-write
```

Без этого флага `serve` остаётся доступным только для чтения. Обладатель общего
токена при включённой записи может менять и удалять опубликованные файлы.

На клиенте укажите существующий каталог и отдельную папку состояния:

```powershell
lansync sync https://127.0.0.1:8765 "C:\Users\dkara\Documents\Received" --state-dir "C:\Users\dkara\Documents\lansync-client-state" --token-file "C:\Users\dkara\Documents\lansync-credentials\token.txt" --ca-file "C:\Users\dkara\Documents\lansync-credentials\ca.pem"
```

Для второго компьютера замените URL на адрес сервера из сертификата и используйте
локальные пути клиента. На Linux используются те же аргументы с Linux-путями.
Папка состояния должна быть вне синхронизируемого каталога, но на том же томе:
это необходимо для перемещения старых файлов в recovery без копирования.
На сервере его папка состояния также должна быть на том же томе, что и Shared.

Не используйте одну папку состояния для разных клиентов. `baseline.json`
привязан к абсолютному локальному пути, URL сервера и идентификатору серверной папки.
Изменение этих параметров требует отдельного состояния и новой первой сверки.

## Правила

### Непрерывная работа

К обычной команде добавьте `--watch --interval 30`:

```powershell
lansync sync https://127.0.0.1:8765 "C:\Users\dkara\Documents\Received" --state-dir "C:\Users\dkara\Documents\lansync-client-state" --token-file "C:\Users\dkara\Documents\lansync-credentials\token.txt" --ca-file "C:\Users\dkara\Documents\lansync-credentials\ca.pem" --watch --interval 30
```

Первый проход начинается сразу, следующие — через 30 секунд после завершения
предыдущего. Проходы не перекрываются; блокировка состояния удерживается до
остановки всего режима. Это работающий процесс в терминале, а не установленная
служба ОС. Остановка — `Ctrl+C`, в том числе во время ожидания.

При разрыве соединения, timeout или HTTP 408/409/429/5xx повторная попытка идёт
через interval, затем удвоенную задержку, максимум `--retry-max` секунд
(по умолчанию 300). После успешного прохода задержка сбрасывается. Интервалы
должны быть положительными конечными числами; retry-max не меньше interval.
Ошибки авторизации, сертификата, привязки папки и другие постоянные ошибки
останавливают процесс с кодом 1. Конфликты файлов не останавливают цикл.

В терминале показываются изменения состояния, новые конфликты и выполненные
операции; одинаковые пустые проходы и одинаковые повторные ошибки не печатаются.
`loop-status.json` в папке состояния обновляется каждый проход и содержит
состояние, последнюю успешную сверку, количество последовательных ошибок и
задержку повтора. `last-sync.json` остаётся отчётом последнего завершённого прохода.
После Ctrl+C код завершения — 0; неразрешённые конфликты остаются в отчёте.

Опрос по таймеру выбран для обнаружения и локальных, и серверных изменений.
Пока каждый проход полностью сканирует оба дерева; уведомления сервера и
инкрементальная проверка самого манифеста — отдельная будущая оптимизация.

После успешного согласования клиент запоминает содержимое и ревизию объекта.
При следующем проходе сравниваются локальная копия, серверная и эта общая база.

| Изменение | Действие |
|---|---|
| Только на клиенте | Передать серверу с базовой серверной ревизией |
| Только на сервере | Скачать или применить удаление локально |
| Обе стороны одинаковы | Зафиксировать совпадение без передачи |
| Обе стороны различаются | Сообщить о конфликте; не менять этот путь |
| Удаление против изменения | Сообщить о конфликте |
| Первая сверка, разные существующие копии | Сообщить о конфликте |

На первой сверке отсутствующий объект обычно копируется с другой стороны.
Но известная серверная отметка удаления не затирается неизвестной старой копией
нового клиента — это конфликт. Переименование представляется удалением и созданием.
Смена типа «файл ↔ каталог» требует ручного разрешения.

Серверные исключения применяются и к локальному обходу; исключённые пути не
отправляются и не удаляются. Между устройствами проверяются коллизии регистра
и Unicode, даже если каждый локальный каталог отдельно корректен.

Конфликт выводится как `Conflict: путь`, команда возвращает код 2. Оба варианта
остаются на своих устройствах; автоматической конфликтной копии рядом с файлом
пока нет. Для разрешения сначала сохраните нужные варианты под отдельными именами,
затем приведите исходный путь на обеих сторонах к выбранному одинаковому содержимому
и повторите `sync`. Удалять baseline для разрешения конфликта не нужно.
Остальные независимые пути могут синхронизироваться в том же проходе.
Код 0 — завершено без конфликтов, 1 — ошибка выполнения.

## Состояние и восстановление

- `baseline.json`: последняя подтверждённая общая версия по каждому пути.
- `last-sync.json`: итог завершённого прохода и список конфликтов.
- `sync.lock`: запрещает одновременный запуск двух клиентов с одной папкой состояния.
- `recovery/<id>.bak` и `<id>.json`: предыдущие версии файлов и исходные пути.

Recovery создаётся и на сервере, и на клиенте перед заменой или удалением файла.
Автоматической очистки пока нет — размер растёт по мере изменений. Для ручного
восстановления остановите обмен, найдите исходный путь в JSON и скопируйте
соответствующий `.bak` в отдельную папку для проверки.

После аварийного завершения может остаться `sync.lock`. Убедившись, что процесс
`sync` больше не работает, удалите только этот lock и повторите команду. Сохранённые
baseline и recovery оставьте. Если сервер принял файл, но ответ потерялся, следующий
проход обнаружит одинаковое содержимое и согласует базу без повторной записи.

## Протокол и ограничения

Манифест версии 2 дополнен `sync_protocol: 1`, `writable` и `revision` в записях.
Ревизии хранятся в отдельной таблице SQLite и не зависят от `generation` обхода.
Они меняются при изменении содержимого, типа или признака удаления; изменение
одного лишь времени файла не создаёт ревизию. Записи об удалении сохраняются.

`PUT /v1/change` принимает параметры `path`, `base_revision`, `kind`, `sha256`,
`size` и двоичное тело файла. Для отсутствовавшего пути базовая ревизия — 0.
Сервер проверяет тело, повторно сканирует затронутый путь и сравнивает ревизию под
блокировкой. Устаревшая ревизия возвращает 409 без применения запроса.
Изменения через API сериализуются одним процессом сервера.

Не запускайте несколько серверных процессов или `watch` с той же серверной БД.
Внешние пользовательские изменения обнаруживаются повторным обходом и проверкой
содержимого перед применением; атомарной транзакции всей папки с файловой системой
нет. Локальные каталоги должны оставаться доверенными, как описано в NETWORK.md.
Отдельные уже успешные операции сохраняются даже при последующей ошибке.
Снимок манифеста может устареть в ходе прохода — повторная команда выполняет сверку.

Полный обход выполняется при запросе манифеста и при первой записи после запуска
сервера, если ещё не было полной сверки. Перед и после последующих записей
перепроверяется только затронутый путь; для каталогов — также их поддерево.
Имена соседей вдоль пути проверяются без чтения их содержимого, чтобы обнаружить
внешнее создание конфликтующего имени после выдачи манифеста. Изменения других
файлов подхватываются следующей полной сверкой.
Проверка ревизий и JSON-представление пока обрабатывают весь индекс в памяти,
поэтому общая стоимость записи всё ещё зависит от количества записей.

## Разрешение конфликта файла

Остановите `sync --watch` через Ctrl+C. Выполните обычный `sync`, чтобы записать
актуальные версии конфликтов, и просмотрите обе копии. Затем выберите версию:

```sh
lansync resolve https://192.168.0.10:8765 "$HOME/Shared" "notes.txt" --choose local --state-dir "$HOME/lansync-client-state" --token-file "$HOME/credentials/token.txt" --ca-file "$HOME/credentials/ca.pem"
```

`--choose local` передаёт локальную версию серверу; `--choose remote` принимает
серверную. Путь файла относителен корню, с разделителями `/`. Команда обрабатывает
только выбранный путь. Остальные конфликты остаются в отчёте. После разрешения
возобновите обычную синхронизацию.

Последний отчёт sync содержит `conflict_versions`: снимки локального содержимого
и серверной ревизии. При отличии от снимка resolve отказывается менять файл:
повторите sync и заново рассмотрите конфликт. Старые отчёты без снимков требуют
нового прохода sync. Передача использует проверку ревизии и SHA-256, заменяемая
копия сохраняется в recovery соответствующего узла. Если выбранная сторона
удалила файл, выбор этой стороны применяет удаление с сохранением другой копии.
Каталоги, смена типа и коллизии имён требуют ручного разрешения.

Коды: 0 — завершено без оставшихся конфликтов, 2 — конфликты остались,
1 — ошибка, включая устаревший снимок. Команда использует ту же блокировку
состояния, что sync. Атомарного снимка двух устройств нет: новые изменения после
операции обнаруживаются следующим проходом. Конфигурационный run пока поддерживает
только scan/watch/serve/pull/sync; resolve запускается явной командой.

## Резервные копии

Просмотр копий на нужном узле (сервер и клиент имеют отдельные recovery):

```sh
lansync recovery list --state-dir "$HOME/lansync-client-state"
lansync recovery list --state-dir "$HOME/lansync-client-state" --json
```

Вывод содержит ID, исходный относительный путь, размер, SHA-256 и наличие .bak.
Просмотр не хеширует содержимое. Повреждённые метаданные показаны как error;
отсутствующие .bak — available=false. Метаданные без .bak могут остаться после
незавершённой операции. Копии без JSON не включаются в список.

Восстановление по ID из списка:

```sh
lansync recovery restore ID --state-dir "$HOME/lansync-client-state" --output "$HOME/restored-notes.txt"
```

Родительский каталог output должен существовать. Команда копирует данные во
временный файл, проверяет размер и SHA-256 и публикует результат без перезаписи
существующего файла. Копия и метаданные в recovery сохраняются. Путь назначения
задаётся явно и должен находиться вне папки состояния. Рекомендуется восстановить
в отдельную папку, проверить содержимое, затем перенести в синхронизируемый каталог:
обычная синхронизация распространит изменение. Восстановление прямо в общий
каталог при работающем обмене может сразу передать файл другому устройству.
Символические ссылки на recovery, метаданные и .bak не поддерживаются.
Код 0 — успех, 1 — ошибка; list возвращает 0 и для записей с полем error.

## Предварительный просмотр

Добавьте `--dry-run` к обычной команде `lansync sync` с URL, root,
state-dir и сертификатами. Для TOML задайте `dry_run = true` и `watch = false`.
Вывод перечисляет upload, download, delete_local, delete_remote и конфликты.
Ничего не передаётся через файловые endpoints, локальные файлы, baseline,
recovery и last-sync.json не изменяются. При первой проверке клиентская папка
состояния не создаётся. Счётчики обычных операций остаются нулевыми:
запланированные операции перечислены отдельно.

Клиент запрашивает манифест: сервер выполняет обычный обход и может обновить
свой индекс и ревизии, но содержимое общей папки не меняется. Требуется сервер
с --allow-write, как и для обычного sync. Режим несовместим с --watch.
При наличии sync.lock просмотр отказывается запускаться. Сам просмотр не
удерживает блокировку; не запускайте параллельно другой sync с тем же состоянием.
План относится к текущему снимку и не гарантирует успех следующего прохода:
файлы, права и соединение могут измениться; непустые каталоги при реальном
удалении по-прежнему защищены. Для применения уберите --dry-run.
Код 0 — план без конфликтов, 2 — есть конфликты, 1 — ошибка.

План можно получить в JSON: добавьте `--dry-run --json` к sync или задайте
`dry_run = true`, `json = true`, `watch = false` в TOML. Поле `planned` содержит
операции и относительные пути, `conflicts` — конфликтные пути. Это предварительный
план, счётчики выполненных операций равны нулю. Без --dry-run флаг --json запрещён.
При --log-file stdout остаётся JSON; код завершения выводится в stderr и журнал.
Для перенаправления JSON в файл используйте `> plan.json`, не объединяя stderr.

Новые отчёты last-sync.json содержат completed_utc (время завершения с часовым
поясом UTC), duration_seconds (длительность прохода) и operation (sync/resolve).
Время записывается для завершённого прохода, в том числе с конфликтами, и не
означает отсутствия конфликтов. Dry-run эти поля в состояние не записывает.
Команда status показывает их и предупреждает, если loop-status.json старше
последнего прохода. В JSON это поле loop_report_older: true/false, либо null,
если дат для сравнения нет. Старые отчёты без новых полей поддерживаются.
Сравнение отражает записанное время, а не проверку работающего процесса;
изменение системных часов может повлиять на порядок дат.

## Проверка целостности recovery

```sh
lansync recovery verify --state-dir "$HOME/lansync-client-state"
lansync recovery verify --state-dir "$HOME/lansync-client-state" --json
```

Команда читает все пары .json/.bak, проверяет размер и SHA-256 каждой копии
и продолжает проверку остальных записей при ошибке одной записи. Статусы:
verified — совпадение; corrupt — несовпадение размера/хеша; missing — нет .bak;
orphan — .bak без метаданных; error — ошибка чтения или формата метаданных.
В JSON возвращаются entries, total, verified, problems. Код 0 — проблем нет,
2 — найдены проблемные записи, 1 — ошибка доступа к самому хранилищу.
Пустое хранилище возвращает 0 и total=0: это не подтверждение наличия копий.
Проверка ничего не удаляет и не восстанавливает. Она читает весь объём копий,
поэтому для большого recovery может занять время. Остановите sync/serve перед
проверкой: в работающей системе пара файлов может быть ещё не дописана.
Файлы с расширениями, отличными от .json/.bak, не входят в проверку.
Совпадение с метаданными подтверждает целостность пары, но не её подлинность.

## Незавершённая замена после сбоя

Перед переносом старого файла в recovery записывается `<id>.pending.json`.
После успешной операции запись удаляется. При ошибке выполняется возврат старой
копии; если он успешен, служебные записи неуспешной замены удаляются. Если возврат
невозможен, .bak и pending сохраняются. Новый клиентский проход отказывается
работать, а сервер возвращает 409 до сканирования, чтобы отсутствие файла
не распространялось как намеренное удаление.

При такой ошибке остановите sync/serve. Прочитайте path и backup в pending,
сохраните .bak через recovery restore в отдельный файл и проверьте его. Восстановите
нужное содержимое по исходному пути, сохранив существующие варианты отдельно.
Только после проверки состояния удалите соответствующий pending вручную;
baseline и резервную копию сохраняйте. Не удаляйте pending только для снятия блокировки.
recovery verify может показывать pending как ошибочную запись метаданных —
это служебный маркер, требующий отдельного рассмотрения.

Автоматические тесты моделируют разрыв чтения, ошибку ENOSPC при публикации,
успешный и неуспешный откат, блокировку следующего прохода и серверного манифеста.
Это не испытание реального отключения питания: гарантии fsync каталога и
автоматическое восстановление после аварийного завершения остаются дальнейшей работой.

## Быстрый запуск обмена по локальным событиям

К команде sync добавьте `--watch --local-events --event-debounce 0.5`.
В общей конфигурации:

```toml
watch = true
local_events = true
event_debounce = 0.5
interval = 30
retry_max = 300
```

Наблюдатель запускается перед первой сверкой. Создание, изменение, перемещение
и удаление внутри локальной папки запускают следующий проход раньше interval.
События объединяются в фиксированное окно event_debounce после обнаружения
сигнала (по умолчанию 0.5 секунды); непрерывные изменения не продлевают его.
События чтения и изменения времени каталога из-за дочернего файла игнорируются.
Наблюдатель только выставляет сигнал: сетевые проходы выполняются последовательно.
События, поступившие во время прохода, вызывают дополнительную сверку.

Периодический опрос сервера остаётся: interval — максимальное обычное ожидание
после завершения прохода. При сетевых ошибках файловые события не сокращают
задержку повторного подключения. Ctrl+C останавливает наблюдатель и освобождает
блокировку состояния. Опция local_events требует watch=true; действия проекта
once и plan отключают наблюдение автоматически.

Каждый проход по-прежнему полностью сканирует обе стороны. Это ускорение реакции,
а не инкрементальный сетевой индекс. Записи, сделанные самим обменом, могут вызвать
один дополнительный проход. События исключённых файлов также могут разбудить
цикл, но файлы остаются исключёнными при сверке. На файловых системах, где native
наблюдение не работает, используйте обычный периодический режим без local_events.

## Прогресс и объёмы передачи

Для sync используйте --progress, в TOML — `progress = true`. Прогресс печатается
в stderr, поэтому stdout режима --dry-run --json остаётся корректным JSON.
Показываются путь, направление, число переданных байт и размер. События
started/transferring/completed/conflict/failed поступают из ядра через on_progress;
обновления transferring ограничены одним сообщением примерно за 0.25 секунды.
completed означает завершение операции и запись baseline, а не только чтение
всех байт. Для каталогов и удалений размер равен нулю. Dry-run не передаёт данные
и не генерирует событий прогресса. Callback выполняется синхронно; GUI должен
быстро помещать событие в свою очередь, не блокировать и не выбрасывать исключения.

Отчёт завершённого прохода содержит uploaded_bytes/downloaded_bytes и operations
с путём, видом операции и размером. Это объём успешно применённых полезных данных,
без TLS/HTTP накладных расходов и без неуспешных передач. При ошибке прохода
last-sync.json остаётся отчётом предыдущего завершённого прохода; прогресс не
заменяет журнал транзакций. status показывает итоговые объёмы. План содержит
planned_upload_bytes/planned_download_bytes и размер каждой планируемой операции.
Счётчики не являются измерением пропускной способности сети.

## Наблюдение за состоянием

```sh
lansync status --state-dir ./client-state --watch --interval 1
lansync run client.toml --action monitor
lansync run client.toml --action monitor --json
```

Монитор читает сохранённые отчёты раз в секунду (для прямого status интервал
настраивается). Он не запускает синхронизацию, не связывается с сервером и
не изменяет состояние. Повторно выводятся только изменившиеся снимки.
Если папка ещё не создана или отчёт временно недоступен, монитор сообщает об
этом и продолжает ожидание. Остановка Ctrl+C возвращает 0.

В режиме --json выводится NDJSON: один JSON-объект на строку. Поля observed_utc,
available и snapshot либо reason позволяют подключить внешний интерфейс.
Это не один JSON-массив. Время observed_utc означает момент наблюдения,
а не время синхронизации. Поле lock_present не доказывает, что процесс жив.
Состояние сервера в сети монитор не проверяет; для этого используйте doctor.
Статус обычной команды run --action status остаётся однократным, даже если
в проекте watch=true. monitor использует собственный интервал 1 секунду.

## Сохранить обе версии конфликта

```sh
lansync run client.toml --action resolve --path notes.txt --choose both --copy-path notes-local.txt
```

Остановите фоновый sync и выполните once для актуального снимка конфликта.
--copy-path — новый относительный путь внутри общей папки; родительский каталог
должен уже существовать. Он не должен существовать ни локально, ни в серверном
манифесте (включая отметку удаления), попадать под исключения или создавать
коллизии переносимых имён. Явное имя позволяет сохранить нужное расширение файла.

Сначала проверенная локальная версия копируется под указанным именем, затем
исходный путь получает серверную версию. Отчёт содержит preserved_copy.
Обычный следующий sync передаст новый файл серверу. Команда resolve работает
только с выбранным конфликтом и не запускает общий обмен остальных файлов.

Если после создания копии скачивание завершилось ошибкой, копия остаётся:
проверьте её, выполните обычную сверку и повторно рассмотрите конфликт. Повторный
выбор занятого copy-path отклоняется. Сохранение копии и замена исходного пути
не являются одной атомарной операцией. Действуют обычные проверки снимка,
серверного хеша и локального состояния перед заменой; предыдущая версия также
сохраняется в recovery. Для удаления против изменения и конфликтов каталогов
выбор both не поддерживается — используйте local/remote либо ручное разрешение.
