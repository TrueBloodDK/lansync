# Двусторонняя синхронизация с ревизиями

Команда `sync` выполняет один проход обмена. Она отправляет новые/изменённые
локальные файлы, скачивает серверные изменения и передаёт удаления. Каталоги
создаются вместе с родителями, удаляются только пустыми, начиная с самых глубоких.
Фонового сетевого цикла пока нет; для следующей сверки повторите команду.

Подготовка сертификатов и токена описана в [NETWORK.md](NETWORK.md).

## Запуск

Обновите установку: `python -m pip install -e ".[dev]"`.
Уже настроенный сервер запустите с дополнительным флагом `--allow-write`:

```powershell
lansync serve "C:\Users\dkara\Documents\Shared" --state-dir "C:\Users\dkara\Documents\lansync-state" --host 0.0.0.0 --token-file "C:\Users\dkara\Documents\lansync-credentials\token.txt" --cert-file "C:\Users\dkara\Documents\lansync-credentials\server.pem" --key-file "C:\Users\dkara\Documents\lansync-credentials\server-key.pem" --allow-write
```

Без этого флага `serve` остаётся доступным только для чтения. Обладатель общего
токена при включённой записи может менять и удалять опубликованные файлы.

На клиенте укажите существующий каталог и отдельную папку состояния:

```powershell
lansync sync https://127.0.0.1:8765 "C:\Users\dkara\Documents\Received" --state-dir "C:\Users\dkara\Documents\lansync-client-state" --token-file "C:\Users\dkara\Documents\lansync-credentials\token.txt" --ca-file "C:\Users\dkara\Documents\lansync-credentials\ca.pem"
```

Для второго компьютера замените URL на адрес сервера из сертификата и используйте
локальные пути клиента. На Linux используются те же аргументы с Linux-путями.
Папка состояния должна быть вне синхронизируемого каталога, но на том же томе:
это необходимо для перемещения старых файлов в recovery без копирования.
На сервере его папка состояния также должна быть на том же томе, что и Shared.

Не используйте одну папку состояния для разных клиентов. `baseline.json`
привязан к абсолютному локальному пути, URL сервера и идентификатору серверной папки.
Изменение этих параметров требует отдельного состояния и новой первой сверки.

## Правила

После успешного согласования клиент запоминает содержимое и ревизию объекта.
При следующем проходе сравниваются локальная копия, серверная и эта общая база.

| Изменение | Действие |
|---|---|
| Только на клиенте | Передать серверу с базовой серверной ревизией |
| Только на сервере | Скачать или применить удаление локально |
| Обе стороны одинаковы | Зафиксировать совпадение без передачи |
| Обе стороны различаются | Сообщить о конфликте; не менять этот путь |
| Удаление против изменения | Сообщить о конфликте |
| Первая сверка, разные существующие копии | Сообщить о конфликте |

На первой сверке отсутствующий объект обычно копируется с другой стороны.
Но известная серверная отметка удаления не затирается неизвестной старой копией
нового клиента — это конфликт. Переименование представляется удалением и созданием.
Смена типа «файл ↔ каталог» требует ручного разрешения.

Серверные исключения применяются и к локальному обходу; исключённые пути не
отправляются и не удаляются. Между устройствами проверяются коллизии регистра
и Unicode, даже если каждый локальный каталог отдельно корректен.

Конфликт выводится как `Conflict: путь`, команда возвращает код 2. Оба варианта
остаются на своих устройствах; автоматической конфликтной копии рядом с файлом
пока нет. Для разрешения сначала сохраните нужные варианты под отдельными именами,
затем приведите исходный путь на обеих сторонах к выбранному одинаковому содержимому
и повторите `sync`. Удалять baseline для разрешения конфликта не нужно.
Остальные независимые пути могут синхронизироваться в том же проходе.
Код 0 — завершено без конфликтов, 1 — ошибка выполнения.

## Состояние и восстановление

- `baseline.json`: последняя подтверждённая общая версия по каждому пути.
- `last-sync.json`: итог завершённого прохода и список конфликтов.
- `sync.lock`: запрещает одновременный запуск двух клиентов с одной папкой состояния.
- `recovery/<id>.bak` и `<id>.json`: предыдущие версии файлов и исходные пути.

Recovery создаётся и на сервере, и на клиенте перед заменой или удалением файла.
Автоматической очистки пока нет — размер растёт по мере изменений. Для ручного
восстановления остановите обмен, найдите исходный путь в JSON и скопируйте
соответствующий `.bak` в отдельную папку для проверки.

После аварийного завершения может остаться `sync.lock`. Убедившись, что процесс
`sync` больше не работает, удалите только этот lock и повторите команду. Сохранённые
baseline и recovery оставьте. Если сервер принял файл, но ответ потерялся, следующий
проход обнаружит одинаковое содержимое и согласует базу без повторной записи.

## Протокол и ограничения

Манифест версии 2 дополнен `sync_protocol: 1`, `writable` и `revision` в записях.
Ревизии хранятся в отдельной таблице SQLite и не зависят от `generation` обхода.
Они меняются при изменении содержимого, типа или признака удаления; изменение
одного лишь времени файла не создаёт ревизию. Записи об удалении сохраняются.

`PUT /v1/change` принимает параметры `path`, `base_revision`, `kind`, `sha256`,
`size` и двоичное тело файла. Для отсутствовавшего пути базовая ревизия — 0.
Сервер проверяет тело, повторно сканирует состояние и сравнивает ревизию под
блокировкой. Устаревшая ревизия возвращает 409 без применения запроса.
Изменения через API сериализуются одним процессом сервера.

Не запускайте несколько серверных процессов или `watch` с той же серверной БД.
Внешние пользовательские изменения обнаруживаются повторным обходом и проверкой
содержимого перед применением; атомарной транзакции всей папки с файловой системой
нет. Локальные каталоги должны оставаться доверенными, как описано в NETWORK.md.
Отдельные уже успешные операции сохраняются даже при последующей ошибке.
Снимок манифеста может устареть в ходе прохода — повторная команда выполняет сверку.

Для простоты сервер выполняет полный обход перед и после каждой записи.
Это рабочий прототип согласования, но массовая синхронизация пока дорога:
следующий этап оптимизации — обновление серверного индекса только по затронутым путям.
