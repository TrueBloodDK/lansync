# Установка и запуск LANSync

## Установка пакета

Требуется Python 3.11+. Создайте окружение вне исходников:

Сервер разворачивается на Linux. Клиент поддерживает Linux и Windows.

```sh
python -m venv lansync-env
```

Linux: `lansync-env/bin/python -m pip install /path/to/lansync-0.1.0-py3-none-any.whl`.
Windows: `lansync-env\Scripts\python.exe -m pip install C:\path\lansync-0.1.0-py3-none-any.whl`.
Зависимости устанавливаются из индекса pip. Это Python-пакет, не автономный бинарник.
Далее используйте lansync из bin (Linux) или Scripts (Windows) этого окружения.
Для обновления остановите процессы и установите новый wheel с `pip install --upgrade --force-reinstall`.
Перед обновлением сохраните конфигурации, состояние и recovery.

## Новый проект

```sh
lansync init ./server-project --mode server
lansync init ./client-project --mode client --url https://192.168.0.10:8765
```

Родительский каталог должен существовать, каталог проекта должен быть новым.
Создаются project.toml, shared и credentials. Клиент включает наблюдение за
локальными событиями; сервер разрешает изменения и удаления по общему токену.
Команда не открывает firewall. Для создания сертификатов установите extra setup:
`python -m pip install "lansync[setup]"`; для локального wheel добавьте [setup]
к пути файла в команде pip install. Затем:

```sh
lansync credentials create --host 192.168.0.10 --output-dir ./server-project/credentials
lansync credentials export-client --source-dir ./server-project/credentials --output-dir ./client-bundle
```

Передайте ca.pem и token.txt из client-bundle в client-project/credentials
доверенным способом. Каталог назначения должен быть новым или пустым.
Для нескольких адресов повторяйте --host. Сертификаты предназначены для частной
LAN-сети; клиент доверяет переданному CA. Ключ CA не сохраняется: для новых
адресов создайте новый комплект и обновите CA на клиентах. Секреты не печатаются.
На POSIX файлы создаются с правами 0600, новый каталог — 0700; на Windows
действуют унаследованные разрешения профиля пользователя. Существующий пустой
каталог сохраняет свои права. Ошибка записи может оставить частичный комплект;
не используйте его и подготовьте новый пустой каталог после проверки.
Приватный ключ клиенту не передавайте. IP в клиентском URL должен входить в сертификат.

```sh
lansync run ./client-project/project.toml --check
lansync run ./client-project/project.toml --action doctor
lansync run ./client-project/project.toml --action plan
lansync run ./client-project/project.toml
```

## Linux: пользовательская служба systemd

Если система использует systemd, создайте ~/.config/systemd/user/lansync.service,
подставив абсолютные пути. Сначала проверьте тот же запуск вручную.

```ini
[Unit]
Description=LANSync synchronization

[Service]
Type=simple
ExecStart=/home/USER/lansync-env/bin/lansync run /home/USER/client-project/project.toml
Environment=PYTHONUNBUFFERED=1
Restart=on-failure
RestartSec=15
TimeoutStopSec=90

[Install]
WantedBy=default.target
```

Команды: `systemctl --user daemon-reload`, `systemctl --user enable --now lansync`,
`systemctl --user status lansync`, `journalctl --user -u lansync -f`.
Остановка: `systemctl --user stop lansync`.
Стандартный SIGTERM завершает текущий проход синхронизации, записывает
`stopped` и освобождает `sync.lock`; ожидание следующего прохода прерывается.
Так же останавливаются команды `watch` и `status --watch` (включая `run --action monitor`).
Новые проходы не запускаются. Сигнал не обрывает текущую передачу или обход:
для больших деревьев увеличьте TimeoutStopSec с учётом времени полного прохода.
request_timeout ограничивает сетевые ожидания, а не суммарную длительность прохода.
Повторный SIGTERM также запрашивает штатную остановку, не ускоряя её принудительно.
Сервер обрабатывает SIGTERM средствами Uvicorn; для него можно создать отдельную
службу с тем же шаблоном, указав server-project/project.toml.
Пользовательская служба обычно связана с сеансом пользователя; запуск без входа
в систему требует отдельной настройки администратора. Не включайте log_file
с постоянным именем: при перезапуске существующий файл отклоняется. Используйте journal.
После принудительной остановки проверьте sync.lock и pending-записи по SYNC.md.

## Windows: запуск при входе

В Планировщике заданий создайте задачу для своего пользователя с триггером
«При входе в систему». Программа — абсолютный путь к lansync-env\Scripts\lansync.exe.
Аргументы: `run "C:\Users\USER\client-project\project.toml"`.
Рабочий каталог — папка проекта. В параметрах выберите «Не запускать новый экземпляр»,
отключите ограничение общей длительности задачи. Для первого испытания выберите
запуск только при входе пользователя. Повышенные права приложению не требуются.
Для фонового запуска без консольного окна можно выбрать pythonw.exe из окружения
и аргументы `-m lansync run "...\project.toml"`; состояние проверяется через status.
Остановка задачи может быть принудительной: перед следующим запуском проверьте
блокировку по SYNC.md. Не запускайте одновременно ручной sync с тем же состоянием.
Это инструкция настройки задания, не установленная Windows-служба.

## Проверка выпуска разработчиком

```sh
python -m pip install build
python scripts/release_check.py --output ./release-new
```

Создаются wheel и sdist, затем отдельное чистое venv. Wheel устанавливается
с зависимостями, выполняется pip check, запуск CLI, init, проверка TOML и scan.
Все smoke-команды выполняются вне репозитория без PYTHONPATH. Требуется интернет
для сборочных зависимостей и установки пакетов. Проверка не заменяет сетевые
испытания и полный набор unittest. Каталог output должен быть новым.

После успешной проверки release_check сохраняет verification.json: среду Python,
платформу и SHA-256 wheel/sdist. Отчёт создаётся только после прохождения smoke-теста.
Хеши позволяют сопоставить проверенный пакет с передаваемым файлом; цифровой подписью
они не являются. Исходный архив включает инструкции, примеры и сценарии сборки.

## Автоматическое испытание установленного пакета

На Linux release_check запускает из чистого окружения отдельный сервер на свободном
loopback-порту и клиентские процессы. После генерации сертификатов проверяются:
HTTPS/doctor, dry-run без изменения клиентского состояния, Unicode и пустые
объекты, двоичная передача, обновления, удаления в обе стороны, конфликт и выбор
версии, проверка recovery, восстановление без перезаписи и совпадение хешей деревьев.

Сценарии описаны в scripts/acceptance.py. На Windows проверяются установка пакета,
клиентский проект, конфигурация, комплект доверия и scan; серверные HTTPS-сценарии
помечаются как skipped в verification.json. Проверка клиента Windows с сервером Linux
выполняется отдельно на сетевом стенде, см. docs/CROSS_PLATFORM_TEST.md.
Сервер ограничен 127.0.0.1; firewall не меняется. Серверный процесс завершается
после проверки, временные проекты удаляются вместе с временным окружением.
Это обычное завершение тестового стенда, не проверка аварийного восстановления.

Дополнительно проверяются сохранение обеих версий конфликта, непрерывный обмен,
повторные попытки при недоступности сервера, его штатный перезапуск и автоматическое
переподключение клиента. Клиент останавливается SIGTERM и запускается заново
с прежним состоянием: проверяются освобождение блокировки и совпадение файлов.

Для повторения без пересборки пакета на Linux (установлен extra `[setup]`):

```sh
python scripts/acceptance.py --cli /absolute/path/to/venv/bin/lansync --output ./acceptance-new
```

Каталог output должен быть новым. В нём остаются изолированные тестовые проекты,
журналы сервера/клиента и verification.json с результатом passed/failed.
Не публикуйте весь каталог: проекты содержат тестовый токен и приватный ключ.
Для передачи результатов используйте verification.json. Сервер слушает только
127.0.0.1, правила firewall и постоянные службы не создаются. Процессы завершаются
и при ошибке; вынужденное завершение по тайм-ауту считается ошибкой проверки.
Сценарий проверяет отдельные процессы на одной Linux-машине, не соединение двух ВМ
и не автозапуск systemd после входа или перезагрузки. Ошибка ранней подготовки
аргументов или каталога выводится в терминал до создания отчёта.

verification.json содержит результаты сценариев и pip freeze установленного
окружения. При ошибке HTTPS-испытания сохраняется отчёт failed и серверный журнал,
если он успел появиться; команда возвращает ненулевой код. Ошибки самой сборки
или pip выводятся в терминал и не создают успешного отчёта. Логи не включают
содержимое сертификатных ключей или токена. Этот тест не заменяет проверку двух
разных ОС по физической локальной сети и не измеряет производительность.

## Повторяемый нагрузочный прогон Linux

```sh
python scripts/soak.py --cli /absolute/path/to/venv/bin/lansync --output ./soak-new --duration 600 --files 500 --large-mib 64
```

Нужен установленный LANSync с extra `[setup]`. Запускаются отдельные сервер и клиент
по HTTPS на loopback. Сначала передаются `files` файлов по 4096 байт и крупный файл
в каждом направлении. Затем в течение `duration` секунд чередуются изменения
и удаления на двух сторонах. Каждое изменение ожидает завершения синхронизации;
это последовательная нагрузка, не тест конкурентного редактирования.

Время подготовки не входит в duration. Параметр `--timeout` (по умолчанию 180 секунд)
ограничивает ожидание одной операции; общая длительность может превысить duration.
Крупные файлы остаются в дереве и участвуют в последующих полных сканированиях.
В конце проверяются SHA-256 всех файлов, каталоги, recovery и освобождение блокировки.

Новый output содержит `verification.json`, текущий `progress.json`, журналы,
проекты и тестовые секреты. Не публикуйте весь каталог. Сценарий не удаляет результаты
и не использует пользовательские каталоги синхронизации. При ошибке сохраняется
отчёт failed; существующий output не перезаписывается.

RSS читается из `/proc` каждые 0,5 секунды: пик между выборками может быть пропущен.
Задержка и эффективные MiB/s включают ожидание опроса, сканирование, хеширование,
HTTPS и запись состояния. Это не измерение чистой скорости LAN и не доказательство
отсутствия утечек памяти. Продолжительность испытаний указывайте вместе с результатами.
Завершение штатное через SIGTERM; отключение питания и SIGKILL не проверяются.

## Измерение передачи между разными машинами

На выделенном тестовом Linux-сервере, из Python-окружения с LANSync `[setup]`:

```sh
python scripts/lan_benchmark.py prepare-server --host 192.168.0.108 --port 8877 --output ./lan-server-new --sizes-mib 64 256
lansync run ./lan-server-new/server/project.toml
```

Сервер привязывается к указанному IP. Разрешите этот порт в firewall только
от адреса клиента. Доверенным способом передайте `client-bundle` и `fixture.json`
на Linux- или Windows-клиент. На клиенте используйте Python с установленным LANSync:

```sh
python scripts/lan_benchmark.py run-client --url https://192.168.0.108:8877 --bundle ./client-bundle --fixture ./fixture.json --output ./lan-client-new
```

Команда создаёт отдельный клиентский проект и проверяет, что сервер точно содержит
исходный набор файлов из fixture. Затем измеряет один проход загрузки всего набора
и один проход передачи такого же объёма обратно. SHA-256 проверяются отдельно
на клиенте и по заново прочитанному серверному манифесту. Время отдельных файлов
также сохраняется через callback прогресса. `--timeout` задаёт тайм-аут сетевых
ожиданий, по умолчанию 120 секунд; это не предел времени всей проверки.

`verification.json` содержит passed/failed, объёмы, времена и эффективные МиБ/с.
Они включают обход дерева, SHA-256, HTTPS, диск и состояние — не только сеть.
Файлы генерируются детерминированно, замер выполняется однократно и не является
универсальной оценкой производительности. Для повторения создайте новые серверный
и клиентский проекты: сервер с результатами предыдущего прогона будет отклонён.
Отчёты позволяют сравнивать стенды только с учётом ОС, дисков, размера файлов и сети.

После завершения остановите сервер и удалите временное правило firewall.
Скрипт самостоятельно не запускает сервер и не меняет firewall; тестовые данные
остаются для проверки. Не публикуйте токен, ключ сервера и весь каталог стенда.

## Локальная проверка перед запуском

```sh
lansync inspect ./client-project/project.toml
lansync inspect ./server-project/project.toml --json
```

Рекомендуемый порядок: run --check → inspect → run --action doctor → plan → запуск.
inspect читает реальную конфигурацию и проверяет корневую папку, расположение
состояния и служебных файлов, одинаковый том для recovery, существующие sync.lock
и pending-маркеры, формат токена, загрузку CA, совместимость серверного сертификата
и ключа, доступность родительского каталога журнала и занятые имена ротации.

Команда возвращает все доступные результаты, не останавливаясь на первом
отсутствующем файле. Непригодная к загрузке конфигурация проверяется отдельно
через run --check. Код 0 — перечисленные локальные проверки прошли, 1 — есть
ошибки. JSON содержит ok, command и checks (check/ok/detail). Токен и ключи
не включаются в отчёт. Файлы не создаются, блокировки не снимаются, сеть не используется.

Оценки прав через os.access предварительные: они не заменяют реальную операцию
записи, не измеряют свободное место и не гарантируют доступ ко всем файлам дерева.
Существующий lock требует выяснить, работает ли процесс; inspect не считает
его автоматически устаревшим. Загрузка пары сертификат/ключ не проверяет срок
действия и соответствие IP сервера: это проверяется TLS-подключением через doctor.
Успех inspect не гарантирует успех последующей синхронизации при изменении среды.
