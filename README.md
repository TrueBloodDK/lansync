# LANSync — индекс файловой системы и наблюдение

Учебный проект системы синхронизации файлов в локальной сети.
Реализованы полное сканирование, индекс SQLite, JSON-манифест и непрерывное
наблюдение через watchdog и минимальное одностороннее скачивание по HTTPS.

Сетевые команды `serve` и `pull`: [пошаговая инструкция](NETWORK.md).
Двусторонняя команда `sync`, ревизии и конфликты: [инструкция](SYNC.md).
Для непрерывного обмена используйте `sync --watch --interval 30`.

## Установка

Требуется Python 3.11 или новее. Команды выполняются из папки проекта.
На Windows вместо `python` при необходимости используйте `py -3`.

```sh
python -m venv .venv
```

Активация в PowerShell: `.\.venv\Scripts\Activate.ps1`.
Активация в Linux: `source .venv/bin/activate`.

```sh
python -m pip install -e .
lansync --help
```

Сканер использует стандартную библиотеку Python; наблюдение — watchdog;
сеть — FastAPI, Uvicorn и HTTPX.
Для установки пакета pip может потребоваться доступ к индексу пакетов.

## Использование

Windows:

```powershell
lansync scan "C:\Users\User\Documents\Shared" --state-dir "C:\Users\User\Documents\lansync-state"
```

Linux:

```sh
lansync scan "$HOME/Shared" --state-dir "$HOME/lansync-state"
```

Указанный каталог должен существовать. Повторите команду после изменения
файлов: индекс обновится, исчезнувшие объекты получат `deleted: true`.
Перемещение пока представляется удалением старого пути и появлением нового.

В папке состояния создаются `index.sqlite3` и `manifest.json`.
Экспорт можно перенаправить аргументом `--manifest /path/to/manifest.json`.
Состояние и экспорт должны находиться вне сканируемой папки.
Каждой корневой папке нужна отдельная папка состояния.

Без `--state-dir` состояние хранится в `%LOCALAPPDATA%/lansync` на Windows
или `$XDG_STATE_HOME/lansync` (по умолчанию `~/.local/state/lansync`) на Linux.
Подкаталог выбирается по хешу абсолютного пути.

Коды завершения: `0` — полное сканирование; `1` — ошибка запуска/экспорта;
`2` — есть ошибки чтения или исключённые объекты, манифест неполный.

## Непрерывное наблюдение

```powershell
lansync watch "C:\Users\User\Documents\Shared" --state-dir "C:\Users\User\Documents\lansync-state"
```

```sh
lansync watch "$HOME/Shared" --state-dir "$HOME/lansync-state" --debounce 0.5 --interval 60 --max-delay 5
```

Наблюдатель запускается до первоначального сканирования. Файловые события
помещаются в ограниченную очередь, а повторяющиеся пути объединяются.
Хешируются только затронутые файлы. Создание, удаление или перенос каталога
обрабатывается вместе с его потомками; при переносе проверяются оба пути.
Изменение каталога из-за записи дочернего файла не запускает обход всего дерева.
Поток watchdog не читает файлы и не обращается к SQLite: это делает основной
рабочий цикл. События открытия и закрытия без записи игнорируются, чтобы
чтение файлов самим сканером не создавало бесконечные повторные обходы Linux.

- `--debounce`: период тишины перед обработкой пачки событий, по умолчанию 0.5 с.
- `--max-delay`: максимум ожидания пачки при непрерывных событиях, 5 с.
- `--interval`: период полной сверки после завершения предыдущей полной сверки, 60 с.

Все интервалы должны быть конечными положительными числами. Время самого
обхода не входит в максимальную задержку: большой каталог обновляется дольше.
События во время обхода остаются в очереди для следующей обработки.
Частые события не откладывают периодическую полную сверку. При переполнении
очереди или накоплении 4096 разных путей выполняется полная сверка.
Ошибки чтения попадают в журнал и манифест; периодическая сверка повторяет
попытку даже без новых событий. Ошибка БД или экспорта завершает процесс
с кодом 1. Пропущенные объекты делают манифест неполным, но наблюдение продолжается.

Остановка — `Ctrl+C` (код 0): поток наблюдения останавливается, база закрывается.
При следующем запуске полный обход обнаружит изменения, сделанные за время
простоя. Полное хеширование выполняется при запуске, по таймеру и при
переполнении очереди. SQLite перезаписывает только изменившиеся записи;
экспорт JSON и чтение индекса пока охватывают всё дерево.

API observer использован согласно [документации watchdog](https://python-watchdog.readthedocs.io/en/latest/quickstart.html).

## Исключения и совместимость имён

Параметр `--exclude` доступен для `scan` и `watch` и может повторяться:

```powershell
lansync watch "D:\Shared" --state-dir "D:\lansync-state" --exclude "*.tmp" --exclude ".git" --exclude "build/*"
```

Правила задаются явно при каждом запуске; автоматических исключений нет.
Совпадение чувствительно к регистру на обеих ОС. Шаблон без `/` проверяется
для каждого компонента пути: `cache` исключает все такие каталоги и их содержимое,
а также файлы с этим именем. Шаблон с `/` применяется к относительному пути
от корня и его предкам. Поддерживаются `*`, `?`, `[abc]` как в Python fnmatch;
`*` может захватывать `/`, особой семантики `**` нет. Исключение родителя
исключает всё поддерево. Это не синтаксис gitignore: отрицания `!`, ведущий
и завершающий `/`, обратные слеши и компоненты `.`/`..` не поддерживаются.
Для каталога используйте `cache`, а не `cache/`.

Исключённые объекты не читаются и не хешируются. Их старые записи сохраняются
в SQLite, но отсутствуют в `entries` манифеста, включая старые отметки удаления.
Добавление исключения не означает удаление на других устройствах.
Обнаруженные исключённые пути перечислены в `skipped` с причиной `excluded by rule`;
такие записи сами по себе не делают манифест неполным. Активные шаблоны находятся
в `exclude_patterns`. Изменение правил требует нового полного обхода — при
перезапуске `watch` он выполняется автоматически. После снятия исключения
содержимое перепроверяется, отсутствующий ранее известный файл отмечается удалённым.

Проверка переносимости имён работает независимо от ОС. Она проверяет
зарезервированные имена устройств Windows, запрещённые символы, пробел/точку
на конце, длину компонента (255 байт UTF-8 и 255 единиц UTF-16), а также
коллизии после NFC-нормализации и casefold. Последнее — консервативная политика
проекта, а не точная эмуляция сравнения имён любой файловой системы.
Проверяются и имена родительских каталогов. Полная длина целевого пути зависит
от места назначения и пока не проверяется.

Проблемные записи остаются в индексе, не переименовываются и перечисляются
в `portability_errors`; `complete` становится `false`, `scan` возвращает код 2.
В режиме `watch` ошибки выводятся в журнал, наблюдение продолжается.
После исправления имён ошибки пересчитываются по всему активному индексу;
удалённые и исключённые записи не участвуют в проверке.
Сетевой модуль отказывается передавать неполный манифест.

Правила Windows сверены с [документацией Microsoft](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).

## Формат и гарантии

Версия манифеста теперь 2: добавлены `exclude_patterns`, `portability_errors`
и различие между исключёнными по правилам и неподдерживаемыми объектами.
Существующая SQLite-база читается без сброса; следующий обход экспортирует версию 2.
Верхние поля манифеста: `schema_version`, `device_id`, `folder_id`,
`generation`, `complete`, `errors`, `skipped`, `entries`.
Пути внутри `entries` относительные, разделитель — `/`.
Файлы имеют размер, время изменения и SHA-256; каталоги — тип и время,
а размер и хеш равны `null`. Пустые каталоги учитываются.

Хеширование выполняется блоками по 1 МиБ. Параметры файла проверяются
до и после чтения. При обнаруженном изменении файл отмечается ошибкой;
повторная попытка выполняется следующим запуском `scan` или сверкой в `watch`.
Каждое полное сканирование заново хеширует все доступные файлы;
обработка событий хеширует только затронутые пути.

SQLite обновляется транзакционно. JSON записывается во временный файл
и заменяет предыдущий экспорт после завершения записи. Сбой экспорта
не откатывает уже сохранённый индекс; повторите команду.

При любой ошибке сканирования новые удаления не фиксируются в текущей пачке.
При частичном обходе удаление допускается только внутри проверенных путей.
Ошибки и исключённые объекты из других путей сохраняются до их повторной проверки.
Старые записи недоступных файлов остаются в индексе, но `complete: false`
и `errors` сообщают, что это не подтверждённое текущее состояние.
Ссылки, Windows reparse points и специальные файлы исключаются;
предыдущие записи под исключёнными путями сохраняются без отметки удаления.

`generation` — номер локального сканирования, не серверная ревизия.
Идентификаторы сейчас относятся к локальному индексу; привязка нескольких
устройств к общему каталогу появится на этапе сетевого протокола.

## Тесты

Для полного набора тестов установите дополнительные зависимости:

```sh
python -m pip install -e ".[dev]"
```

Тесты выполняются стандартным unittest; trustme создаёт временные TLS-сертификаты:

```sh
python -m unittest discover -s tests -v
```

Без установки, PowerShell:

```powershell
$env:PYTHONPATH = "src"
python -m unittest discover -s tests -v
python -m lansync --help
```

Linux: `PYTHONPATH=src python -m unittest discover -s tests -v`.
Тесты также совместимы с pytest (`pip install -e ".[dev]"`).

## Ограничения и следующие этапы

### Автоматическая проверка платформ

В `.github/workflows/tests.yml` добавлена матрица Windows/Ubuntu и Python
3.11/3.13. После отправки коммита в GitHub она запускается на push и pull request;
доступен и ручной запуск Actions → Python tests → Run workflow.
Наличие workflow само по себе не означает успешной проверки Linux — нужен
завершённый запуск. POSIX-тесты создают реальные несовместимые имена, ссылки
и FIFO; на Windows они пропускаются. Обычные тесты watcher проверяют реальные
события ОС. Настройка основана на [документации GitHub](https://docs.github.com/en/actions/tutorials/build-and-test-code/python).

### Измерения для практики

После установки проекта запустите из его каталога:

```sh
python scripts/benchmark.py --work-dir ../../work/bench-data --output ../benchmark.json
```

Сценарий создаёт собственный временный каталог, по умолчанию 100, 1000 и 10000
файлов по 4096 байт, по три повтора. Пользовательские файлы не затрагиваются.
В JSON сохраняются среда, отдельные результаты и медианы: первоначальный обход
и обработка одного изменённого файла, включая SQLite и экспорт JSON. После
обновления результат сравнивается с независимым полным обходом.

Параметры: `--counts 100 1000`, `--file-bytes 4096`, `--repeats 3`.
Генерация данных и контрольный обход не включены во время операций.
Измерения выполняются с включённым tracemalloc: он добавляет накладные расходы
и измеряет пик Python-выделений, а не полную память процесса (RSS).
Данные только что записаны и могут находиться в файловом кеше; это не тест
холодного диска. Задержка доставки событий watcher и debounce здесь не измеряется.
Для отчёта дополнительно запишите модель накопителя, объём RAM и условия запуска.

Это снимок результатов обхода, а не атомарный снимок файловой системы.
Каталог, который меняется во время обхода, требует повторной сверки.
Проверка параметров файла снижает риск гонки, но не заменяет снимки ОС.
Не запускайте несколько сканирований одной папки состояния одновременно.
Индекс содержит всё дерево в памяти; потоковым является чтение содержимого.

Дальнейшие этапы: оптимизация сверки манифестов и интерфейс разрешения конфликтов.
Поддержку Linux необходимо подтвердить запуском тестов на Linux.

## Запуск из конфигурации

Команда `lansync run client.toml` запускает существующую команду с настройками
из TOML-файла (Python 3.11+). Например:

```toml
command = "sync"
url = "https://192.168.0.10:8765"
root = "./shared"
state_dir = "./client-state"
token_file = "./credentials/token.txt"
ca_file = "./credentials/ca.pem"
watch = true
interval = 2
retry_max = 30
```

Поддерживаются scan, watch, serve, pull и sync. Имена параметров совпадают
с CLI, но дефисы заменяются подчёркиваниями. `exclude = ["*.tmp", ".git"]`
задаёт исключения для scan/watch/serve. Флаги задаются значениями true/false.
Обязательные параметры остаются обязательными; неизвестные ключи отклоняются.
Относительные пути вычисляются от каталога TOML-файла, `~` раскрывается.
В Windows удобно использовать пути с `/` или одинарные строки TOML.
Токен хранится в отдельном файле: конфигурация содержит только путь к нему.
Аргументы поверх конфигурации не поддерживаются — редактируйте сам файл.

Готовые шаблоны: `examples/server.toml` и `examples/client.toml`.
Скопируйте нужный шаблон в рабочий каталог стенда, создайте рядом `shared`,
подготовьте сертификаты по NETWORK.md и измените IP сервера в client.toml.
На сервере выполните `lansync run server.toml`, на клиенте —
`lansync run client.toml`. Серверный шаблон разрешает запись и удаления.
Папки состояния будут созданы автоматически. Не помещайте credentials или
файлы конфигурации внутрь shared.
