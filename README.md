# LANSync

Кроссплатформенная система синхронизации файлов в локальной сети на Python.
Проект дипломной работы; модуль наблюдения и манифеста также используется
для преддипломной практики. Требуется Python 3.11 или новее.

Поддерживаемые роли: сервер — Linux, клиенты — Windows и Linux.
Серверная роль Windows не входит в требования и план приёмочных испытаний.

Текущий список оставшихся работ: [подготовка к выпуску](docs/READINESS.md).

## Возможности

- Полный и событийный обход файловой системы, индекс SQLite, JSON-манифест.
- SHA-256, отметки удаления, исключения и проверка переносимости имён.
- HTTPS с проверкой сертификата и токеном доступа.
- Однократная и непрерывная двусторонняя синхронизация.
- Быстрый запуск сверки по локальным событиям и периодический опрос сервера.
- Предварительный план, обнаружение конфликтов и явный выбор версии.
- Резервные копии перед заменой/удалением, восстановление и проверка целостности.
- Единая TOML-конфигурация, диагностика, статус и журналирование.
- Создание проектов, сертификатов и клиентских комплектов из установленного пакета.

## Установка из исходников

```sh
python -m venv .venv
```

Linux: `source .venv/bin/activate`.
Windows PowerShell: `.\.venv\Scripts\Activate.ps1`.

```sh
python -m pip install -e ".[dev]"
lansync --help
```

Установку wheel и запуск в фоне описывает [INSTALL.md](INSTALL.md).
Для генерации сертификатов достаточно дополнительного набора `[setup]`;
набор `[dev]` включает зависимости тестов. GUI пока нет.

## Быстрый старт

На сервере создайте проект и сертификаты для реального адреса:

```sh
lansync init ./server-project --mode server
lansync credentials create --host 192.168.0.10 --output-dir ./server-project/credentials
lansync credentials export-client --source-dir ./server-project/credentials --output-dir ./client-bundle
lansync run ./server-project/project.toml
```

Разрешите входящий TCP-порт 8765 от клиента в своём firewall. На клиенте:

```sh
lansync init ./client-project --mode client --url https://192.168.0.10:8765
```

Передайте ca.pem и token.txt из client-bundle в client-project/credentials
доверенным способом. Приватный ключ остаётся на сервере. Затем:

```sh
lansync run ./client-project/project.toml --check
lansync run ./client-project/project.toml --action doctor
lansync run ./client-project/project.toml --action plan
lansync run ./client-project/project.toml
```

Адрес в URL должен входить в сертификат. Каталоги проектов при init должны
быть новыми. Шаблон сервера разрешает запись и удаления; токен предоставляет
доступ к опубликованной папке. Остановка процессов — Ctrl+C.

## Команды и документация

| Задача | Команда / документ |
|---|---|
| Сканирование | `lansync scan ROOT --state-dir STATE` |
| Наблюдение и манифест | `lansync watch ROOT --state-dir STATE` |
| Сервер HTTPS / одностороннее получение | `serve`, `pull`; [NETWORK.md](NETWORK.md) |
| Обмен, конфликты, восстановление | `sync`, `resolve`, `recovery`; [SYNC.md](SYNC.md) |
| Работа через один TOML | `run`; [WORKFLOW.md](WORKFLOW.md) |
| Состояние / диагностика | `status`, `doctor` |
| Установка и автозапуск | [INSTALL.md](INSTALL.md) |
| Подтверждённое Windows ↔ Linux испытание | [Отчёт](docs/CROSS_PLATFORM_TEST.md) |

`run --check` проверяет конфигурацию, но не доступность сети и файлов.
Для JSON используйте --json в поддерживающих его командах. Для журнала
scan/watch/serve/pull/sync/resolve доступен --log-file: файл должен быть новым,
вне общей папки и состояния, родительский каталог должен существовать.
Ротация — 5 МиБ и три архива. Используемый токен редактируется в журнале;
пути и ошибки могут содержать личные данные. Для фонового запуска используйте
журнал службы, не постоянное имя --log-file.

## Гарантии и ограничения

Состояние хранится вне общей папки. Для sync и writable-сервера оно должно
быть на том же томе: предыдущие версии перемещаются в recovery. Не используйте
одно состояние в нескольких процессах. Конфликт не разрешается автоматически.
Перед ручным разрешением остановите непрерывный клиент.

Манифест содержит относительные пути, размеры, время изменения и SHA-256.
Переименование представляется удалением и созданием. Права, владельцы и время
изменения файлов между устройствами не переносятся. Символические ссылки,
специальные файлы и Windows reparse points не синхронизируются. Проверка имён
консервативна и учитывает совместимость с Windows и коллизии Unicode/регистра.

Каждый сетевой проход пока сканирует обе стороны полностью. Передача файла
потоковая, но манифест и индекс обрабатываются в памяти; сетевой манифест ограничен
16 МиБ. Возобновления с конкретного байта и передачи изменённых блоков нет.
Нет атомарного снимка всей папки и защиты от злонамеренной подмены локальных
каталогов другими процессами. Работайте с доверенными локальными папками.

Recovery автоматически не очищается. Незавершённые замены с pending-маркерами
блокируют дальнейшую сверку до проверки человеком. Испытания реального
аварийного выключения питания отложены. Данные для испытаний храните отдельно
от единственных экземпляров важных файлов.

## Проверка и измерения

```sh
python -m unittest discover -s tests -v
python scripts/benchmark.py --counts 100 1000 --repeats 3 --work-dir ./bench-work --output ./benchmark.json
python -m pip install build
python scripts/release_check.py --output ./release-new
```

Benchmark сравнивает полный обход и обработку одного изменения, включая SQLite
и экспорт JSON. Он измеряет выделения Python через tracemalloc, не RSS процесса;
данные могут находиться в кеше, задержка доставки событий не измеряется.
release_check собирает wheel/sdist и проверяет установку с зависимостями
в отдельном чистом venv вне исходников. В CI настроены Windows/Ubuntu и
Python 3.11/3.13; результат конкретного запуска нужно смотреть в Actions.
